v8 UPDATE — DISPLAY SYNCHRONIZATION
Retain the check that clearing never precedes VBI acknowledgement ($42=0).
Final-RAM tests do not detect all display-timing errors. Hiding the wait
behind work that does not write the image requires proof of data
independence and a gain >=0.05 FPS. A third buffer requires RAM/ANTIC
analysis; extra ROM alone is insufficient. These ideas were not implemented.
Items 5–8 of the earlier audit remain deferred.

v7 UPDATE / 0.05 FPS THRESHOLD
Further geometry specialization (+0.1162 FPS) and fast clipping
(+0.0760 FPS) were implemented. Other tested minor ideas below 0.05 FPS
were rejected; see historical WYDANIE_V7_PL.txt and candidate-estimates.json.
Items 5..8 of the earlier audit remain deferred. Cross-frame caching has
neither a demonstrated correctness contract nor a credible gain budget.
No absolute optimum is claimed; further implementation requires a new
candidate with justified gain >=0.05 FPS and preserved game results.

FUTURE DIRECTIONS — HYPOTHESES, NOT CONFIRMED GAINS

1. Bitmap clearing $9214: initial profile about 5.4% of machine time.
   Investigate unrolled STA abs instead of STA abs,X, buffer specialization,
   and code-size cost. First count dynamic stores/cycles, then compare
   all RAM and FPS. Better candidate than further tiny sound savings,
   but this copy has no verified new implementation.
2. Filling $9308: still significant. Consider larger write blocks and
   address tables; account for first row, edges, masks, and both buffers.
   Do not add inclusive time shares to the costs of child routines.
3. Code layout: count branches and reads crossing pages. Loop/table
   placement may save a cycle without algorithm changes; a new layout
   may worsen other branches. Measure actual data, not just random inputs.
4. Mountain profile: cautiously improve the fully-occluded test. Preserve
   the conservative extra-height bound and scan every column. More
   aggressive rejection must be proven not to remove visible mountains.
5. Interpolation $7EEB: try partial unrolling or code placement without
   bank switches rather than a full version in bank6. Preserve LSR/ADC
   order, carry, and destructive operand changes. The current experiment
   did not improve mean FPS over sound-only changes.
6. Multiplication $7CD6: unchanged so far. Early exit when the operand
   becomes zero makes naive eight-step unrolling non-obvious. Test full
   operand/flag state, not just the numerical result.
7. Sound: marker helper adds a call on the event path. Investigate moving
   the loop tail and using a jump instead of nested JSR. Idea only,
   unimplemented/untested. With many events, the current flag change can
   cost more than the original; retain tests of all 14 channels, priority
   ties, and POKEY write ordering.
8. 128 KiB cartridge: potentially more specializations and result tables,
   at the cost of banking and mapper compatibility. Current v3 needs only
   64 KiB and has empty bank6, so first use available space. Larger size
   alone does not speed up the CPU. No measured 128 KiB version yet.
9. Method: prepare more independent flights/levels and a fixed-renderer-
   input test with cycle counting. Small FPS differences may come from
   VBI synchronization and changing later scenes. Do not select only
   trials in which the new variant wins; publish regressions too.

Acceptance conditions: matching live state/image and required flags,
safe interrupts/banks, restart support, separate integration cost, then
full-game measurement. Matching POKEY write values/order alone does not
justify claiming sample-by-sample audio equivalence.
